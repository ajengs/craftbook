# D1 — Bug investigation

**Entry:** A bug, from one of two sources: the user starts Artifex in `defect` mode on a bug ticket, or a P5 run reports a **major finding** (`workflows/P5-verification.md`) and the user agrees to investigate it. **Start:** the umbrella creates and starts this session in place of P1 and P2, when `route` prints D1 as the start. A bug needs no kickoff or analysis unless the user asks for one. For a P5 finding it also links the new `milestones/<id>/` folder to the milestone and the finding in `state.json`. **Owners:** the investigation agent, and the user where the path below asks for approval.

**Inputs:** The ticket, or the P5 finding with its evidence; the code and environment access the user confirms, and the telemetry and artifacts the environment offers. For a P5 finding, the milestone's PR and the head it was verified on.

**Documents:** `diagnosis.md` (`templates/diagnosis.md`). It replaces the specs, the verification contract and the verification handoff for this bug. It is human-targeted on every path, like the kickoff, analysis and specs: the user reads it and comments on it whether or not it needs approval.
- Before drafting, run `artifex_state.py doc surface diagnosis --milestone <id>` and draft on the surface it prints (`SKILL.md`, Documents): a Claude Docs page on Claude Code, the local file in its annotating viewer on Codex. Don't keep a plain-markdown draft and move it later. Process passage or visual annotations as focused revisions while preserving the rest of the document.
- The path only decides approval. On Confirm, the user approves the revisions below. On Direct and Reproduced there is no approval step: the document is there to read, and a comment can still redirect the fix or move the bug to Confirm. Before writing the handoff, export the revision it references to `milestones/<id>/diagnosis.md`.
- Keep the root-cause and fix-approach approvals in the same document, each against a named revision. On each approval, ensure the approved `diagnosis.md` derived copy exists and that its reference or hash is recorded as `SKILL.md`, Documents requires.

**Codes:** internal codes stay in notes. Keep them out of the reproduction, tests, commits, the PR and the ticket (`policies/core.md`).

1. **Symptom, place and evidence.** Restate the symptom as reported, with where and on which version it was seen, and don't guess at causes yet. Ask the user once for the branch and working directory (checkout or worktree) the fix will be made on; for a P5 finding the default is the milestone's PR branch.
   - For a bug that comes from a ticket, collect what the available telemetry and artifacts show before building the reproduction: metrics, traces, logs, debug recordings, profiler captures and dumps, for the reported instance and time window (`SKILL.md`, Optional tools). Record in `diagnosis.md` each source you used, with its type, a link or path, the instance and time window or version, and what it showed; also record what was unavailable and what wasn't checked. Someone reading the diagnosis should be able to open every source it cites. Beyond the source list, put the proof itself in the diagnosis, as `standards/evidence.md`, Evidence in one file, describes: sample exceptions, the stack traces, log lines, metric values with their links, screenshots, whichever exist. A path to a raw output or analysis file backs an excerpt; it never replaces one. Evidence can locate the cause when no reproduction is possible, but the fix still follows the reproduction rule in step 7.
   - For a P5 finding, start from P5's evidence and add telemetry only where it doesn't identify the cause. Cite the P5 verification report and its raw evidence references as sources, with the head it was verified on.
2. **Reproduction.** Build a command that goes red on this symptom, with the debug loop tool (`SKILL.md`, Optional tools), phases 1 to 4. It must be deterministic, fast, runnable unattended, and assert the reported symptom rather than a nearby failure. Minimise it until every remaining element is load-bearing. Give each reproduction a `REP-` code in the diagnosis's Reproduction table and record its kind: automatic, manual (steps a person runs) or none.
   - Revert temporary instrumentation and working-tree edits at the end; D1 commits and pushes nothing. Save the reproduction files in the milestone folder and name the run command.
   - When the reproduction is a regression test the fix adds and the user's standing rules keep D1 from building or running it (no build or run unless asked), don't run it and don't offer it as an open decision: the REP row says "not run in D1: P3 shows it red", and P3 runs it red before the change (`workflows/P3-implementation.md`, step 3). That counts as the red run step 7 requires. Ask the user only when the reproduction needs something P3 can't do either, such as production-only data, a customer site or manual steps.
   - If no reproduction can be built, say what was tried and ask the user for access to a reproducing environment, a captured artifact, or permission to add temporary instrumentation. Don't hypothesise past that.
3. **Root cause.** Rank 3 to 5 falsifiable hypotheses before testing any, test them one variable at a time, and name the cause with its evidence, marking what was observed and what is only inferred. Say what was ruled out.
4. **Fix approach.** The exact change (files and methods), what stays as it is, where a regression test can assert the symptom (no correct seam is itself a finding), and the same cause elsewhere.
5. **Path.** Pick one, and record in `diagnosis.md` which conditions are met and how they are shown.

| Path | Conditions | User approval |
|---|---|---|
| Direct | The cause is observed, not inferred. The change is small and exact (named files and methods, one component) and the evidence is conclusive. A regression test can assert the symptom. Confidence is high | None |
| Reproduced | The reproduction is automatic and red, and goes green on the proposed change in a scratch copy | None |
| Confirm | Anything else: the cause is inferred, the reproduction is manual or missing, or more than one fix is reasonable | The root cause first, then the fix approach |

   Whatever the path, a fix that needs a design decision (a contract, schema or data change, or behavior beyond the symptom) belongs to the user: use Confirm for that decision. When the fix is large enough to need a design of its own, D1 can propose a P2 design session in its Confirm report. Once the user approves, the umbrella starts P2 with the diagnosis as the milestone's scope link (`milestones` row `link`), and the specs, not the fix approach, then drive the implementation.
6. **Direct or Reproduced.** Write the implementation handoff right away with the handoff writer (`SKILL.md`, Optional tools), referencing the diagnosis revision (`templates/implementation-handoff.md`, frontmatter included, and the diagnosis's own `auto_agent`, `manual_agent` and `manual_user` frontmatter filled). Notify the umbrella with the path, the conditions met, the diagnosis document's link and revision, and the exported diagnosis and handoff paths and revisions. The umbrella starts the implementation worker and posts one line with the diagnosis link, saying a bug fix started without approval and why, so the user can redirect it.
7. **Confirm.** Present the diagnosis for root-cause approval with the best reproduction in hand, and the user approves a revision. On that first root-cause approval, give the compaction reminder (`SKILL.md`, Execution efficiency, Phase-session compaction): the fix approach is drafted from the approved document, not from the investigation transcript. Then add the fix approach and the user approves that revision. The fix does not start without a solid reproduction: red, run at least once, and matching the reported symptom. A regression test D1 may not run under the user's rules meets this through P3's red run before the change (step 2), with no decision to ask. A manual reproduction is run by the user and also becomes a manual scenario (P6). With none, the user decides what to supply or explicitly accepts fixing without one, and the umbrella records that as a risk. After the fix-approach approval, write the handoff as in step 6; the approval is the go-ahead and the handoff has no approval of its own.
8. **In flight.** The user can move a bug between paths at any time, in either direction ("ask me before fixing", "just fix it"). The umbrella records the change in `state.json` and it takes effect at once. If the implementation worker on Direct or Reproduced finds that its change doesn't turn the reproduction green, or that the fix needs a design decision, it stops and reports to the umbrella, which sends the bug back to D1 on Confirm. That is not a rework and counts toward no cap.

**From a P5 finding.** The fix goes on the milestone's PR through the usual P3 and P4 path and counts as one of the 2 reworks after P5 failures (`SKILL.md`, Rework cap). A bug outside the milestone's changes gets its own PR, and whether it blocks the milestone's closure is the user's decision, which the umbrella asks for.

**Verification.** Reproductions (`REP-`) prove the bug; verification scenarios (`VER-`) prove the fix. Keep them in separate sections of the diagnosis. Its Verification section stands in for the verification contract and the verification handoff, so give it the same shape as P2's contract (`templates/verification-contract.md`, `standards/specifications.md`): high-level `VER-` scenarios, each with a type, one run category, the reproductions it covers, what to check, the evidence to collect and a pass condition, then the tools and evidence by run, user interactions, environment and limitations. Read `references/verification-tools.md` for the per-run tools, evidence purposes and readiness plan. Categories: `auto_agent` (P5 after P4 passes), `manual_agent` (P6 on an explicit user trigger, fully agent-executed), or `manual_user` (P6 with specified user interactions). A manual reproduction performed by the user belongs to `manual_user`.
- **Every diagnosis has VER-001, reproduction verification, as `auto_agent`.** It covers every `REP-` row: each must fail before the change (P3's recorded red run) and pass on the PR head, with the sibling symptoms the diagnosis lists. A REP with no red run, or not green on the PR head, fails it. When every REP is a regression test the fix adds, P3 already runs each one red before the change and green on the head it pushes, so VER-001 adds nothing a P5 run would: list it in the frontmatter's `p3_evidence` too. The router then skips P5 for it, and P4 checks that P3's red and green runs are recorded for the head it reviews. Leave VER-001 out of `p3_evidence`, so P5 runs it, when a REP is not a regression test (a manual reproduction, or one that needs an environment, data or a benchmark), or when the diagnosis asks for the run on a head other than P3's.
- A reproduction that needs an environment, data or a benchmark gets its own `VER-` scenario on the PR head, in its selected category. Only `auto_agent` runs in P5; `manual_agent` and `manual_user` run in explicitly triggered P6. An environment or benchmark does not override the chosen category.
- A performance bug's reproduction is a benchmark: design it with the benchmark designer (`SKILL.md`, Optional tools), and the diagnosis points to its contract.

From the implementation handoff on, P3 to P6 run as usual. D1 stays available for change requests relayed by the umbrella and does not monitor P3 to P6. When a later decision or finding changes the diagnosis (a changed choice, a follow-up ticket id, a correction from P3), D1 edits the diagnosis so it holds the current value, and logs the value it replaced with `artifex_state.py supersede` (`SKILL.md`, Boundaries).

**Output:** `diagnosis.md`, the reproduction files, and the implementation handoff.

**Exit:** On Direct and Reproduced, the handoff is complete and reported. On Confirm, the fix approach is approved and the handoff is complete and reported.
