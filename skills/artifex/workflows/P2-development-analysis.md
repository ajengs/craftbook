# P2 — Development analysis

**Entry:** One selected milestone plus either (a) approved kickoff and analysis revisions, (b) an approved kickoff revision and the user's explicit small-task scope confirmation, or (c) a scope the user gave in the invocation as a file, a link or a description, with no kickoff or analysis (`milestone` mode, or `implementation` mode without all four artifacts). When the scope lacks context or boundaries, P2 escalates to the user instead of guessing. **Start:** the umbrella creates and starts this session when either complete P1 checkpoint arrives, or when `route` prints P2 as the start. More P2 sessions, one per further milestone or for an ad hoc analysis, start when the user asks the umbrella; each works independently and sends its own handoffs to the umbrella. An ad hoc analysis has no milestone from P1, so the umbrella gives it a `milestones/<id>/` folder id and registers it in `state.json`. **Owners:** User and analysis agent, collaboratively.

**Inputs:** Selected milestone, approved kickoff revision, either the approved analysis revision or the user's recorded small-task scope confirmation, and relevant code/system context. With entry (c) the inputs are the milestone's scope and link in `state.json`, which the brief prints; nothing is assumed beyond them.

**Documents:** specs and verification contract are human-targeted. Review each on the surface `artifex_state.py doc surface` prints (`SKILL.md`, Documents). Handoffs are agent-facing markdown.

**Order:** specs, tradeoffs register, implementation handoff and P3 checkpoint; then verification contract and verification handoff. Specs and contract are approved by the user. Each approval immediately produces its handoff. P2 only produces artifacts and runs no implementation; it remains open while P3 runs and for later change requests.

**Short P2.** The brief for a short P2 (`brief P2 --milestone <id> --short`) lists the artifacts and context the user supplied. Draft the specs and the verification contract in one document on the specs surface. The specs part is approved on its own and produces the implementation handoff and its checkpoint at once (step 6). The contract part is then approved and produces the verification handoff (step 7). Export each approved part to `milestones/<id>/specs.md` and `milestones/<id>/verification-contract.md`. Anything the user supplied, such as a draft specs file, is input to this draft, not an approval.

**Context after approval:** use the approved artifact for the next handoff. Evaluate compaction or a fresh-session handoff under `SKILL.md`, Execution efficiency, when the review conversation has become burdensome; approval itself does not require a restart or delay the implementation checkpoint.

1. Restate the **selected milestone only**: objectives, scope/exclusions, constraints, dependencies.
2. Investigate relevant current behavior and architecture; create a shared **high-level current-state model** with the user.
3. Agree on the **target-state model** and material design choices. Use `standards/design.md`; don't introduce complexity to accommodate speculative edge cases.
4. Draft the Given/When/Then specifications as a table (`templates/specs.md`). Add Constraints and Boundaries only for what isn't already covered elsewhere. List only edge cases that affect requirements, design decisions or scope boundaries, each with `handle`, `defer` or `escalate` (`standards/design.md`). Draft it on the surface `artifex_state.py doc surface` prints for it (`SKILL.md`, Documents); markdown-first means `milestones/<id>/specs.md`. Process passage or visual annotations as focused revisions while preserving the rest of the document. Put the design tradeoffs the user chose, and any lasting limitation that follows, under Tradeoffs and Limitations Accepted, one line each with the boundary at which it would still be a defect. The `defer` edge cases join them.
5. Resolve `escalate` cases with the user, or list them as blocking questions. The user reviews the specs through annotations and approves a specific revision; that approval is also the user's decision on every proposed tradeoff and `defer` row. On approval, ensure the approved `milestones/<id>/specs.md` derived copy exists; the umbrella records the provider revision ID and SHA-256 markdown hash, or the markdown-first path and SHA-256 hash, as required by `SKILL.md`, Documents.
6. **Tradeoffs register, then the implementation handoff, immediately after specs approval.** First create `milestones/<id>/tradeoffs.md` (`templates/tradeoffs.md`, `standards/design.md`, Tradeoffs and limitations register): one row per approved `defer` edge case and accepted tradeoff, each with a first decision-log entry dated today, `who` the user and the approved specs revision as the note. Create it even with no rows, so the handoffs have a fixed path. No separate approval or request; it is agent-facing markdown. Then create the handoff (`templates/implementation-handoff.md`, `standards/specifications.md`): `milestones/<id>/implementation-handoff.md` with the handoff writer (`SKILL.md`, Optional tools), or its fallback, without another approval or request. It is an agent-facing instruction document that an isolated implementation worker, started by the umbrella, can use to implement the milestone, using only the handoff and the approved specs it names. It starts with the template's frontmatter (branch, working directory, target, dependencies), which the router reads; whatever writes it, check that the frontmatter is there and filled.
   - Tell the writer that the implementation worker implements this milestone from the approved specs, and give it the template's headings.
   - Name the branch and the working directory the phase worker works in, and what the handoff depends on, such as another milestone's PR or a merge. Use the ones the user gives. If none, propose the resolved implementation working directory (the user's current checkout) and a branch name; propose a worktree only when the user asks for one or another implementation is already using that checkout. The user confirms either way.
   - If the branch, working directory or target isn't settled when the specs are approved, don't hold the handoff for it: write `TBD` for that frontmatter value and list it under blockers in the checkpoint. The umbrella gets the answer from the user and records it with the router (`event context`); the handoff isn't rewritten and P2 isn't asked again. An unresolved design choice is still a blocker that stops the handoff.
   - Include the implementation rules from the template unchanged unless the user says otherwise.
   - Reference the approved specs revision and do not repeat the specs or require a verification contract. Link `tradeoffs.md` instead of copying its rows.
   - Settle every choice that would change the code's shape if reopened (`standards/specifications.md`). Name the model, reasoning effort and agent type for the run (`SKILL.md`, Model allocation).
   - Name `artifex` and `workflows/P3-implementation.md` as suggested instructions, and name the phase worker `<ticket id> P3 implementation <context>`.
   - Notify the umbrella with the approved specs revision, completed implementation-handoff path and revision, and any blocker. With no blocker, this first P2 checkpoint tells the umbrella to start an isolated implementation worker from the handoff. P2 continues to step 7; it does not stop or monitor it.
7. **Verification contract, after the implementation checkpoint** (`templates/verification-contract.md`, `standards/specifications.md`). Draft and review it on the same review surface as the specs (`SKILL.md`, Documents); markdown-first, create `milestones/<id>/verification-contract.md` before review and keep revising that same file.
   - Decide with the user what the milestone needs: functional verification, a benchmark, or both.
   - List **high-level scenarios**, not scripts, covering what routine test and CI runs don't show: matching each approved spec to a test that covers it, plus, as the milestone needs, user interactions, APIs, workflows and data consistency checks.
   - Prefer extended integration tests that can run without running the app.
   - Mark each scenario **auto** (runs in P5 right after P4 passes) or **manual** (runs in P6 on the user's trigger). A milestone may have no auto scenarios, no manual ones, or both. Say which.
   - Offer the **full PR review** as an optional scenario: the PR reviewer (`SKILL.md`, Optional tools) reviews the whole PR, not only the new commits, in P5. It runs only if the user approves the contract with it included.
   - Benchmark: invoke the benchmark designer (`SKILL.md`, Optional tools) in Draft mode to design the benchmark contract and its runbook. The benchmark session adds the harness it needs. Mark the benchmark auto or manual like any other scenario. The contract is human-targeted and the runbook is agent-facing.
   - Both: one verification contract covers the functional scenarios and points to the benchmark contract for the benchmark part.
   - Where a register row has a boundary that can be checked, such as a limit or a data shape, consider a scenario that shows the boundary holds. Under Material limitations, refer to the rows rather than restating them.
   - The user reviews the contract through comments or annotations and approves a specific revision. On approval, synchronize the approved `milestones/<id>/verification-contract.md` copy and record the exact artifact and file identities required by `SKILL.md`, Documents. The draft is **not** permission to execute anything.
8. **Verification handoff, immediately after verification-contract approval** (`templates/verification-handoff.md`). Create `milestones/<id>/verification-handoff.md` with the handoff writer, or its fallback, without another approval or request. It lists the approved specs and contract revisions, a link to `tradeoffs.md`, the auto and manual scenarios (their ids also go in the template's `auto` and `manual` frontmatter, which the router reads), how to verify them, the evidence destination, and the model and agent type for P5/P6. Notify the umbrella when it is created or modified. P5 cannot start until the approved contract and this handoff are ready.
9. Keep the P2 session available after both checkpoints. Do not monitor P3, P4 or P5. If the umbrella later sends a change request for the specs, contract, either handoff or the register, process that request only. A changed spec or contract needs approval again and any affected handoff must be regenerated before its next consumer starts. A register request carries the user's decision: add or update the row and append its decision-log entry with that decision's date and `who`. It needs no approval and regenerates nothing, unless the decision also changes a spec row or a contract pass condition; that part goes through approval as above.

**Handoff meaning:** writing a handoff creates an agent-facing instruction document; handing off starts the phase worker that consumes it. Specs approval is the go-ahead to write the implementation handoff, and its complete checkpoint tells the umbrella to start the implementation worker automatically. The umbrella starts it, not P2. Verification-contract approval is the go-ahead to write the verification handoff. Neither handoff has a separate approval gate.

**Outputs:** Approved specs and verification contract; the tradeoffs register; implementation and verification handoff documents ready to run in isolated sessions.

**Exit:** Approved specs and verification contract; the tradeoffs register; implementation and verification handoff documents ready to run in isolated sessions. P3 starts from the first checkpoint in step 6. P2 remains available to finish the verification artifacts while P3 runs and to process later change requests.
